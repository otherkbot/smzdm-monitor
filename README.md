# 什么值得买 (SMZDM) 好价监控推送系统

基于 GitHub Actions 的单次扫描脚本。它抓取什么值得买好价列表，先用互动和增长数据筛出候选，再按有代表性的评论等级证据、用户集中度和商品去重规则筛选。重复评论和互动比例异常先记录观察，不直接认定水军。继续覆盖广泛品类，通知列表优先显示价格、商品和已知购买条件，帮助快速判断是否值得点开。

本文档按 `2026-10-11` 的代码与工作流配置更新；实际阈值以 `smzdm.py` 中的 `CONFIG` 为准。[2026-10-10 运行复盘](analysis/smzdm-review-2026-10-10.md)记录了当时的运行证据与问题；[2026-10-11 API 与公开项目调研](analysis/smzdm-api-research-2026-10-11.md)说明本次证据与改动边界。日期报告是历史快照，不替代现行配置。

这是一套广泛发现工具。互动热度能说明社区关注，不能证明商品适合每个人，也不能直接证明同类中质量更好或价格更便宜。推送会展示能确认的理由和条件，帮助快速判断；未核验的价格优势会明确说明，不凭品牌、低价或筛选路径给商品作质量认证。这次展示改动复用已有数据，不增加外部请求。

> **本分支改动（2026-10-17）**：推送通道由 WXPusher 改为企业微信自建应用图文消息（`news`，点卡片直接打开 SMZDM 原文）；新增“关键词低价提醒”（见第 10 节）；热度推送逻辑不变。
>
> **2026-10-18**：新增企业微信群机器人（消息推送）Webhook 通道。配置 `WECOM_WEBHOOK_URL` 后优先走群机器人（同样的 `news` 卡片，无需 corpid/Secret/token）；未配置时继续走自建应用消息。群机器人每分钟最多 20 条，脚本两次发送至少间隔 3.2 秒，遇 `errcode=45009`（超频）等待 60 秒后只重试一次；`errcode=0` 才写入推送历史。日志中 Webhook key 只显示前 4 位。

## 当前逻辑

### 1. 数据源

- 主列表接口：`https://api.smzdm.com/v1/list?limit=100&offset=N`
- 1/3/12 小时热榜补充：`https://m.smzdm.com/sou/category_rank?page=1&limit=50&hour=N`
- 文章延迟复查接口：`https://haojia-api.smzdm.com/detail/{article_id}`
- 频道列表补充接口：`https://api.smzdm.com/v1/faxian/list?...&version=2`、`https://api.smzdm.com/v1/youhui/list?...&version=2`
- 关键词查询：`https://api.smzdm.com/v1/list?keyword=关键词&limit=50&offset=0`（与主列表同一接口的 `keyword` 参数，每个关键词/别名每轮一次请求，单轮最多 10 次）。
- 只扫描 `faxian`、`youhui` 两类频道。
- 主列表负责发现候选和读取互动数据；频道列表用于补充 `article_link`、`article_mall_client.mall_no`、`article_mall_client.product_no`。这些字段不是每条都有，脚本只在接口能提供时使用。
- 主列表每页读取接口实际支持的 100 条上限，最多 51 页/5100 条和过去 6 小时数据。实测接口在 offset 5100 后返回空列表；高峰期 4000 条只覆盖约 1.5 小时，扩到 5100 条约覆盖 1.8 小时，低流量时仍以 6 小时时间窗为上限。
- 热榜配合 15 分钟扫描轮换 1、3、12 小时窗口，每轮仍只发起一次榜单请求，但读取接口单次实际支持的前 50 条。1 小时榜补短期爆发，3 小时榜识别持续升温，12 小时榜补回已经退出主列表但仍在成熟的商品。热榜商品不会直接推送，仍需经过相同的标题、互动质量、评论、趋势和去重规则。
- 有些商品离开主列表和总榜后，评论审核完成、收藏继续增长，列表扫描便无法再看到最新互动。脚本会从历史快照中选择曾经接近门槛但尚未推送的商品，通过文章详情 JSON 读取当前状态、价格、值/不值、收藏和评论数，再走完整筛选流程。
- 延迟复查不是无限回扫：只检查发布不超过 18 小时、旧快照已有 `值 >= 4 且收藏 >= 4`、或 `值 >= 6`、或 `评论 >= 8` 的商品；本轮主列表/热榜已经发现的商品不重复请求。预算按队列积压动态调整为每轮 4–16 条，同一文章至少间隔 45 分钟；优先检查从未复查且最接近 18 小时上限的商品，防止旧候选在首次检查前过期。
- 脚本是单次运行模式：扫描 -> 筛选 -> 推送 -> 退出，没有常驻循环。

### 2. 第一阶段：互动评分初筛

综合评分公式：

```text
综合评分 = 评论数 * 3 + 收藏数 * 2 + 值票数 * 1
```

当前有六条放行路径：

| 路径 | 门槛 | 用途 |
| --- | --- | --- |
| 超级好价 | 评论 >= 20，值 >= 20，收藏 >= 10，综合评分 >= 120，值票支持率 >= 90% | 值票、评论、收藏均充分的成熟商品 |
| 均衡热度 | 评论 >= 6，值 >= 8，收藏 >= 5，互动 >= 25，综合评分 >= 65，值票支持率 >= 90% | 三类互动都较完整的成熟商品 |
| 高讨论 | 评论 >= 12，值 >= 8，收藏 >= 5，互动 >= 30，综合评分 >= 90，值票支持率 >= 85% | 讨论充分且值票、收藏也达到门槛的商品 |
| 早期好价 | 值 >= 4，评论 >= 6，收藏 >= 4，互动 >= 16，综合评分 >= 35，值票支持率 >= 95% | 当前信号较好，并等待后续值票/收藏增长确认 |
| 早期强信号 | 值 >= 6，收藏 >= 8，互动 >= 16，综合评分 >= 28，值票支持率 >= 95% | 评论可能还在审核，以值票/收藏增长确认 |
| 升温好价 | 值 >= 4，收藏 >= 4，互动 >= 15，综合评分 >= 32，值票支持率 >= 95%，且历史快照中至少新增 1 个值票 | 不允许只靠评论或收藏增长进入升温路径 |

值票支持率门槛有一个受控的小样本例外：当值票至少 6、最多只有 1 个不值、实际值票支持率仍不低于 85% 时，可以继续参加均衡、早期或升温路径判断。它仍需满足该路径的评论、收藏、综合评分和趋势要求；出现 2 个不值或值票支持率低于 85% 时不适用。这样可避免 `6 值 : 1 不值 = 86%` 被早期 95% 门槛一票否决。

值票支持率按 `值 / (值 + 不值)` 计算；它只代表值友对这篇爆料的投票，不能解释为商品买家好评率。基础要求：值票至少 2 或评论至少 2。售罄、过期、已结束会直接过滤。

脚本不做大范围标题关键词和分类/tag 硬过滤。流量卡、红包、券、运营商、金融等内容如果互动质量达标，会继续进入后续判断；这类内容建议在 WXPusher 侧用关键词屏蔽。

但 WXPusher 只能做普通关键词，无法表达“入会%京豆”这种中间内容可变的规则。脚本会先归一化全角数字、带方框/按键的数字等常见变体，再拦截任务动作和奖励语境，例如：

- `入会...京豆`
- `入会5豆`
- `关注...1豆`、`关注...京豆`
- `关注领京豆`
- `签到...京豆`、`签到100豆`
- `得10京豆`、`领10京豆`、`送10京豆`
- `抽奖50豆`、`大转盘...50豆`、`竞猜瓜分2万京豆`
- `店铺领5️⃣`、`直播5豆`、`关注45D`、把“豆”写成“逗”的签到/抽奖标题
- 店铺名后只有 `加购/如图`、`共计二十个豆`、`有2 0` 等操作或奖励话术
- `来来来这是一百的` 等没有明确商品主体的含糊标题
- `店铺活动（加购 10）`、`店铺会员入会50`、`积分兑10豆`、`京自领京豆` 等只有店铺任务或奖励、没有可购买商品的标题
- `积分兑换二十五豆`、`专区有二十豆`、`等级礼包五十豆` 等中文数字或拆分数字变体
- `进入弹窗可领随机卡/优惠券`、`10元e卡抽奖`、只有品牌参与信息的促销页
- `积分兑换京豆`、`加购商品得京豆`、`入会20`、`每日一豆` 等省略奖励单位或混入店名的任务
- `会员页...加购有礼，加购4件商品（20）京豆` 等把任务说明和奖励数量拉长的变体
- `弹窗可领红包`、`参加活动非必中`、`深夜游乐场` 等会场、抽奖或含糊活动标题
- `手机馆京豆`、`8月等级礼包15豆`、`15天抢1000豆`、`7天50豆需入会` 等省略动作或奖励单位的任务标题
- 只有店名的 `京东自营旗舰店`、`入会抽奖`、`京东直播...直播间`、`今日好券/好券速领` 等没有具体商品的页面

`入会专享`商品、名称中含“大转盘”的玩具等不会仅凭单个词过滤；任务动作必须同时带有京豆、红包、积分、实测中奖等明确奖励语境。`评论有奖`、`会员积分兑换实物` 等非商品活动会过滤。

纯店铺规则只针对没有具体商品主体的店铺入口。带有商品品类、型号或规格的标题，即使以“官方旗舰店”结尾，也会继续进入正常筛选，例如 `海尔 空调3匹AI舒适风Pro家用一级能效柜机E2旗舰店`。这修正了旧规则把商品描述误认为纯店铺的情况。

单字动作不会脱离奖励单位判断：`圆领...型号D`、`抽油烟机...92D`、品牌名中的“得”和商品名“聚力豆”等不会再被当成领豆任务。

成功推送日志会同时记录文章 ID、价格、筛选路径和互动指标，便于后续从 Actions 日志复盘具体商品。

### 3. 候选快照和趋势评分

脚本会把有基础互动信号的文章写入 SQLite `candidate_snapshots` 表，默认保留 2 天。每次扫描时，同一文章 ID 会和自己的历史快照比较，计算：

- 值票增长、收藏增长、评论增长。
- 总增长分：评论增长权重最高，其次是值票和收藏，不值票增长会扣分。
- 最近一轮增长分。
- 是否出现发布一段时间后互动停滞、需要降噪的候选。

不同爆料文章的互动计数不能互相相减，即使商品 SKU 或标题指纹相同。趋势查询和每轮快照防重都按文章 ID 隔离；旧数据库中使用 SKU/指纹 key 的快照仍能按相同文章 ID 读取。SKU/指纹继续用于商品推送去重。

`升温好价` 依赖这些增长数据。这样刚发布时评论还没审核出来的商品不会被早期评论数误伤；反过来，初始自带一些值和收藏、但后续不增长且评论仍少的商品会被降噪。

历史快照还用于延迟复查队列。商品在主列表可见时即使没有通过初筛，只要已经出现一定互动，就可能在退出列表后被有限次读取最新详情。任务标题会在写入趋势快照前过滤；旧快照进入延迟复查池时，也会先在本地退休任务标题并由后续有效商品补足本轮预算，不会浪费外部详情请求。延迟复查只更新发现能力，不会绕过标题、互动评分、趋势、评论样本、异常检测和去重；详情显示商品已经失效时会退出复查队列。

趋势现在不只是展示和加分，也会参与筛选：

- 低信心早期商品（`早期好价`、`早期强信号`）第一次出现时先保存快照。下一轮必须出现足够快的互动增长，并且至少新增 1 个值票，才会推送；当前数据已经成熟且分布均衡（评论至少 10、综合分至少 65、值至少 6、收藏至少 8），或讨论热度已经充分（评论至少 20、综合分至少 100、值至少 4、收藏至少 8）时可直接通过，避免因最近半小时没有新增值票而无限等待。
- `升温好价` 必须满足近期增长，或在较短累计窗口内达到足够的增长速度，而且至少新增 1 个值票。只增加评论或收藏、或超过几小时才慢慢涨一点的商品不再进入升温路径。
- 已有历史快照、观察至少约 25 分钟、评论仍少、总增长分和最近增长分都偏低的商品会被“增长过低过滤”。
- 如果观察窗口已经很长、评论仍少、最近一轮几乎不涨、累计增长速度也很低，会触发“增长过慢过滤”。
- `超级好价`、`高讨论` 不受低增长/增长过慢过滤影响。

### 4. 评论等级和评论集中度检测

对初筛候选调用移动端详情模块：

```text
https://haojia.m.smzdm.com/detail_modul/user_related_modul?article_id={article_id}
```

从返回 JSON 中读取评论用户的 `vip_level`、`user_smzdm_id`、`display_author` 和模块里的 `author_smzdm_id`。这个模块不是完整评论分页，通常只返回热评/相关评论样本；脚本会记录模块声明的评论总量、原始样本数、作者评论数和非作者样本数。只采集实际 `rows` 及其 `child_list`，按评论 ID 去重；父评论引用和 `aigc_comment_rows` 镜像不会重复计数。缺少等级的评论仍保留，等级记为未知；账号识别使用稳定的 `user_smzdm_id`，不会把相同昵称合并成同一人，缺少账号 ID 也不会变成同一“未知用户”。

如果详情模块声明的评论总数高于列表 API 评论数，脚本会用模块总数更新当前商品的评论数和综合评分。这样像列表只显示少量评论、详情里实际已经有大量评论的商品，不会因为列表数据滞后而继续按“样本不足/早期商品”处理。

脚本先判断评论模块覆盖率：用 JSON 中实际返回的去重评论节点数（包含等级未知和作者评论），对比 `max(列表 API 评论数, 模块声明总评论数)`。只有返回样本覆盖总评论数约 80%，或两者差距不超过 2 条时，才把样本视为具有代表性。模块覆盖不足时，等级和集中度不作为硬拒绝依据。

- Lv5 及以下、Lv6 及以上只是等级特征，不能分别证明水军或真实购买身份。
- 等级比例硬拒绝还要求：排除作者后，至少 6 条样本等级已知，且已知等级覆盖非作者样本至少 80%。在这些条件都满足时，低等级占已知等级超过 35% 才过滤。
- 只有 3–5 条已知等级，或多数等级未知时，等级仅作诊断，不会显示为“等级通过”。
- 代表性模块中，非作者评论样本达到 4 条后仍独立检查集中度，不受 6 条等级门槛影响：
  - 独立用户少于 3 个时过滤。
  - 单个用户评论占比超过 50% 时过滤。
- 集中度先于大评论区少样本放行检查；即使作者回复占多数，剩余 4 条评论来自两个用户，也不会绕过检查。
- 如果评论模块覆盖率足够，且成熟商品只能取到 2 条非作者评论样本，但两条都是 Lv6+ 且来自不同用户，同时商品值票支持率 >= 85%，并且评论数 >= 10 或综合评分 >= 80，则允许继续后续判断，等级仍标为证据不足。
- 如果评论模块覆盖率不足，不再默认阻断推送；脚本会记录评论覆盖诊断，最终主要按互动评分和增长趋势判断。
- 普通早期好价不走少样本通过，避免用少量热评样本误判。
- 早期强信号考虑到 SMZDM 评论审核延迟：当列表评论数低于评论等级判断门槛时，会跳过评论等级判断并继续后续流程；如果评论数已经足够，仍会尝试读取评论等级。

### 5. 评论等级不可用时

评论接口可能返回样本不足、触发外部熔断，或本轮评论校验预算耗尽。现在评论等级不可用只作为诊断信息，不再默认暂缓已经通过互动/趋势评分的商品。

- 本轮评论校验预算是动态计算的：常规情况下校验全部可校验候选，最高 80 条，避免预算不足造成额外半小时级延迟。
- 评论等级不可用时，推送内容会显示评论判断说明。
- 只有模块具有代表性时才允许评论硬过滤；等级比例另需满足至少 6 条已知等级和 80% 等级覆盖，集中度仍从 4 条非作者样本起检查。
- 旧的 `pending_reviews` 表仍保留兼容，但默认策略已经不依赖评论不可用暂缓。

### 6. 评论和互动异常观察

当总投票数达到 30 后，脚本会检查两个异常信号：

- 值/不值比例超过 20。
- 评论数/值票数低于 0.2。

同时命中 2 个比例异常时，只记录观察，不再仅凭“值多、不值少、评论少”拒绝。这些现象也可能出现在正常优惠或评论审核延迟中，不能据此确认账号身份。

新增评论异常观察复用本轮已经取得的非作者评论，无需额外请求。样本至少 6 条时，检查是否有不少于 4 个稳定账号发表相同的长文本（规范化后至少 24 字符），且该重复组占非作者样本至少 60%。排除显式引用块并保留数字、标点含义，不用“真香”“已买”等短句判断水军。

若该重复组每条评论的时间均可解释，且整个时间区间的最宽跨度不超过 180 秒，再记录“重复文本集中出现”的组合信号。`N分钟前` 按一分钟区间处理，`N小时前` 按一小时区间处理，不能把粗粒度时间当成秒级证据。缺时间时仍可观察重复正文，但不能形成集中时间信号。

这些新增信号处于观察模式，不改变放行结果；日志只记录数量、覆盖率、时间跨度上界和文本哈希，不保存或输出评论正文及用户 ID，也不把命中称为已确认水军。

另外，如果一个商品已经被多轮扫描观察到，发布超过 60 分钟后值/收藏/评论几乎没有增长，且评论仍很少，会触发更严格的“增长停滞过滤”。

### 7. 去重和降价再推送

- 企业微信 `message/send` 返回 `errcode=0` 时，才把商品写入 `history`，并把 `msgid` 保存到 `send_record_id`。`errcode=0` 代表企业微信接受了消息，返回中的 `invaliduser` 等字段会记入日志。
- 同一文章 ID 已推送过会跳过。
- 如果频道列表提供了平台商品号 `article_mall_client.product_no`，会生成平台 SKU key，并优先按同 SKU 去重。
- 相似标题会生成商品指纹，30 天内默认只推一次。
- 标题中的价格金额会归一化后再生成指纹，不会因为 `19元套餐`、`22.5元/斤：商品名` 等价格位置导致指纹缺失或重复推送。
- 如果同 SKU 或同指纹商品价格比历史推送低至少 5 元，或降幅至少 5%，允许再次推送，并在推送内容里标记降价信息。对比范围是本项目保留的历史推送价格，不代表全网或市场历史最低价。
- 价格比较排除返还额、满减门槛、券面额和原价；启动时重算历史价格值，校正旧版本误把返还额当售价的记录。
- 未推送或推送失败的商品不会写入历史，下次扫描仍可结合最新互动和候选快照重新评估。
- 旧版 WXPusher “接收人关键词过滤”冷却（`push_keyword_cooldowns` 表）已停用：企业微信没有对应的拒绝语义，发送流程不再写入新冷却。表结构和读取逻辑保留，旧缓存里尚未过期的冷却行仍会被尊重直至到期并自动清理；接收人键改为 `corpid:agentid:touser` 的 SHA-256。
- 企业微信 `access_token` 每轮运行只获取一次并缓存；发送返回 `40001/40014/42001`（令牌无效/过期）时刷新令牌并只重试一次。
- 消息开启企业微信 `enable_duplicate_check`（30 分钟），缓存回滚导致的同一内容重复发送由企业微信侧拦截。
- POST 超时可能意味着发送任务已被服务接受，结果属于未知；脚本记录该情况并不在本轮立即重发，后续扫描仍可能再次评估，因此当前系统不承诺恰好一次投递。

### 8. 京东商品处理

京东自营强校验当前默认关闭。原因是 GitHub Actions 访问京东或跳转页时经常拿不到稳定的店铺/自营字段，强行过滤会误伤好价。

现在京东商品和其他平台一样，统一走互动评分、评论等级、评论集中度、互动异常和去重逻辑。

### 9. 反爬和稳定性

- 外部详情/评论请求有随机延迟。
- 如果遇到 `202/403/429`、验证码、`probe.js`、访问频繁等标记，本轮会熔断外部校验。
- 熔断后不再继续请求详情/评论接口，降低触发反爬的风险。
- 延迟复查详情按积压动态使用 4–16 次请求；连续 2 次失败会熔断本轮外部请求。接口不可用不会阻断主列表扫描，下一次定时任务会重新恢复。
- GET 请求对 `500/502/503/504` 最多重试 2 次，连接/读取超时分别为 8/20 秒。不按 `Retry-After` 自动等待或重试 `429`，外部接口限流可及时进入本轮熔断，避免长等待占住运行窗口。主列表连续 3 页失败会结束本轮，评论接口连续 2 次失败会熔断外部校验，由下一轮定时任务继续。
- 关键过滤、趋势和推送日志包含文章 ID 与来源；评论诊断记录覆盖情况，趋势诊断记录基准文章及时间。运行汇总分开统计运行推送失败、超时结果未知、用户关键词拒绝、冷却跳过和异常观察，便于区分 Actions 执行成功与通知业务结果。

### 10. 关键词低价提醒

- 配置：环境变量 `SMZDM_KEYWORDS`（非空时优先），否则读取仓库内 `keywords.json`。格式 `好奇号:155,京东plus会员|京东plus年卡:80`：冒号后是价格上限（元），`|` 后是同一规则的别名。
- 匹配：标题经 NFKC 全半角统一、忽略大小写、去掉空格和标点后做包含匹配，因此 `京东PLUS会员`、`京东 PLUS 会员`、`《好奇号》` 都能命中。
- 来源：主列表/热榜扫描中出现的文章，加上每轮对每个关键词/别名主动查询一次（只取 12 小时内的 `faxian`/`youhui` 爆料）。
- 判断：解析出的价格 `<=` 上限即推送；价格无法解析、已售罄/过期、任务活动标题不推送。**不经过热度、评论、趋势筛选**，首次看到即推。
- 去重：按 `history` 中的文章 ID、SKU 和标题指纹去重，每篇文章只推一次（同 SKU/指纹降价达标时仍可再推）；同一轮同一关键词同价的多条重复爆料只推最新一条。
- 标题标记为 `[关键词:好奇号] ¥149 商品名`，描述含价格/购买条件/阈值，并注明“未经热度筛选”。
- 价格沿用通用解析规则：例如 `69.33元（需买3件，共208元）` 取 208 元比较。

## 运行

```bash
pip install -r requirements.txt
WECOM_CORPID=ww... WECOM_AGENTID=1000003 WECOM_SECRET=xxx python3 smzdm.py
# 只看载荷、不发送、不写历史：
DRY_RUN=1 SMZDM_DB_PATH=/tmp/dry.db python3 smzdm.py
```

环境变量：

- `WECOM_WEBHOOK_URL`：可选，企业微信群机器人（消息推送）Webhook 地址；设置后走群机器人，下面四项可不填。
- `WECOM_CORPID`：企业微信企业 ID。
- `WECOM_AGENTID`：自建应用 AgentId。
- `WECOM_SECRET`：自建应用 Secret。
- `WECOM_TOUSER`：接收人 userid，多个用 `|` 分隔，默认 `@all`。
- `SMZDM_KEYWORDS`：关键词低价提醒配置，留空用 `keywords.json`。
- `DRY_RUN`：设为 `1` 时只在日志中打印企业微信载荷，不请求企业微信、不写入推送历史。
- `SMZDM_DB_PATH`：SQLite 数据库路径，默认 `smzdm.db`。

## GitHub Actions

`.github/workflows/smzdm.yml` 当前配置：

- 由 cron-job.org 每 15 分钟触发一次；工作流不再同时配置 GitHub schedule，避免两套定时器造成重复扫描。
- 支持 `workflow_dispatch` 手动触发。
- 手动触发时可选填 `debug_article_id`，先兼容旧缓存的数据库表结构，再打印该文章最近 2 天的候选快照、相同文章/SKU/标题指纹的成功推送历史，以及当前接收人的延迟复查队列位置，用于定位具体漏推或判重原因；留空不影响正常运行。
- 支持 `repository_dispatch`，可由 cron-job.org 请求 GitHub API 触发。
- SQLite 数据库通过 `actions/cache` 恢复和保存。
- 使用 `concurrency: smzdm-scan` 避免同仓库扫描任务并发执行。
- 单次任务最长运行 12 分钟，避免故障任务占住后续 15 分钟扫描窗口。
- 扫描前运行单元测试，失败时停止本轮，避免带着已知回归继续推送。
- 需要的仓库配置（Settings → Secrets and variables → Actions）：Secrets `WECOM_WEBHOOK_URL`（群机器人，优先）或 `WECOM_CORPID`、`WECOM_AGENTID`、`WECOM_SECRET`（自建应用）；可选 Variables `WECOM_TOUSER`（默认 `@all`）、`SMZDM_KEYWORDS`（留空用 `keywords.json`）、`DRY_RUN`。

本次保留每 15 分钟执行：2026-10-10 复盘中最近 100 次平均约 4 分钟完成，且 72 次已读满 5100 行；提高频率会增加重复请求，降低频率会延迟早期信号和第二次趋势观察。少数未启动脚本的 hosted runner 故障由下一轮恢复，不额外立即重跑。这个判断针对上述样本，后续可依据漏推、时延和外部限流再调整。

注意：`actions/cache` 不是严格的可变数据库存储。如果多个运行非常接近，仍可能恢复到较旧缓存，导致短时间重复推送。需要更可靠的长期状态时，应选用具备明确读写与并发控制的持久化存储；当前系统不承诺恰好一次投递。

## 推送内容

企业微信图文消息（`news`）每条一张卡片：标题为“价格 + 简短商品名”（关键词提醒为 `[关键词:xx] ¥价格 商品名`，最多 128 字节）；描述第一行沿用下面的摘要，随后是平台/发布时间和值/不值/评论/收藏/路径（最多 512 字节）；`url` 为 SMZDM 原文，链接无效时回退到 `https://www.smzdm.com/p/{id}/`；`picurl` 为商品图。按 UTF-8 字节截断，不截断多字节字符。

摘要先显示价格和已知购买条件，再显示简短商品名及推送理由。标题去掉开头的促销标签，保留商品主体；从现有标题和价格中识别 `88VIP`、`PLUS会员`、需买 N 件、国补、淘金币、用券、限地区、凑单品、移动端、随机免单活动及晒单/评论奖励等条件。摘要最多 100 字符，完整条件仍需看原文。

摘要将 `PLUS会员`、`需买 N 件`、`需用券` 简写为 `PLUS`、`需 N 件`、`券`，让商品名更早出现在手机短通知里；详情仍保留完整条件。极端复杂价格与条件无法同时容纳时，摘要提示“复杂价格见详情”；异常超长数量提示“数量见原文”。保留商品和未核价说明，完整报价继续显示在详情。

原文链接只接受有效 HTTP(S) 地址，JSON 保留原始查询参数。

返还条件标为“含返E卡/含返积分”，只有原文明说是返还后价格时才标“折算”；`119.9元（返240积分）` 不会被推断为已扣除积分。起价、价格范围、单位价及复杂返还价格保留原语义，详情保留原文价格，并提示分别核对实际支付与返还。

以下 HTML 详情（`_build_notification_content`）是 WXPusher 时期的正文格式，代码与测试保留，企业微信 `news` 卡片不发送 HTML 正文。HTML 详情先展示价格、商品与购买条件，以及能核实的推送理由：同文章实际新增的值票/收藏、当前抓取的热榜位置，或相对本项目历史推送价的真实降价。没有这些信号时展示当前值票和评论数；不会编造“史低”“必买”等结论。没有历史降价标记时，摘要提示“价差未核实”，详情提示价格优势待核实；有降价标记也只代表本监控历史推送价的对照，购买条件仍需确认。热榜来源不等于价格优势。

基础互动展示为“值票支持率”及具体值/不值/评论/收藏数。“值票支持率”是 `值 / (值 + 不值)`，不是买家对商品的好评率；小样本 `4 值、0 不值` 的 100% 需结合票数看。

购买链接之后保留简短筛选记录，包括质量路径、互动分、文章观察时长与增长分、评论样本覆盖和等级不可用说明。更完整的评论等级、集中度、声明总数和趋势基准留在执行日志，避免购物详情被算法诊断占满。展示的增长理由只使用有意义的近期窗口，SMZDM 详情链接用于进一步确认商品和下单条件。

（WXPusher 时期）购买入口旁使用 WXPusher 官方 HTML `<copy>` 标签提供“复制商品名”和“复制原文链接”。商品名保留完整型号规格，链接保留原始参数；所有复制属性均转义。复制原文按钮只在链接可用时出现。普通浏览器不能自动实现该标签，本地[通知预览](analysis/notification-preview-2026-10-11.html)提供浏览器复制演示，真实客户端行为以手机端支持为准。

[WXPusher 评估](analysis/wxpusher-review-2026-10-11.md)记录了文档、客户端源码和历史回放。2026-10-11 一次只读实测显示发送状态查询已停用，因此不新增状态轮询；发送任务接受仍不等于终端到达。

- `test_push_keyword_cooldown.py`：旧冷却状态兼容（接收人隔离、到期、快照保留和延迟复查补位）测试。
- `test_webhook_delivery.py`：群机器人 Webhook 载荷、`errcode` 判定、超时、节流、45009 重试与 key 脱敏测试。

- `keywords.json`：默认关键词低价提醒配置。
- `test_comment_evidence.py`：等级证据门槛、未知等级和集中度边界测试。
- `test_comment_anomalies.py`：评论节点解析、引用/镜像防重、正文重复和时间精度观察测试。

- `.github/workflows/smzdm.yml`：GitHub Actions 工作流。
- `README.md`：面向使用者的现行规则和部署说明。
